Manage Multiple AI Tools

5 September 2026

You install a second AI coding tool, paste the same rules into yet another settings panel, and three weeks later one copy has drifted. Keep instructions, skills, and optional bot roles in your git-backed dotfiles, then symlink every tool home at that single source of truth.

The layout below is a worked example from my private ~/dotfiles. Treat the paths and install.sh mapping as a portable pattern to copy into your own repo — private or public — not something to clone from mine.

1. Why One Repo Beats N Config Panels

Most agent tools look for instructions under their own home directory — something like ~/.grok/, ~/.copilot/, ~/.cursor/, or ~/.claude/. Skills usually live in a skills/ folder next to that. If you copy-paste the same markdown into each place, you own N versions of the truth.

A cleaner pattern:

  1. Put the real files in ~/dotfiles (tracked, reviewed, pushable — your repo).
  2. Point each tool’s expected path at those files with symlinks.
  3. On a fresh laptop: pull or clone your repo, run the installer, source your shell helpers.

The repo holds the canonical files; install.sh creates the symlinks each tool expects. Named bots, scheduled routines, and background workers can live in the same tree so a Bot machine and a laptop share one edit path.

2. What a Real Layout Contains

A practical agents-focused tree looks like this (concrete names from my setup — yours can differ):

~/dotfiles/
  agents/AGENTS.md              # shared always-on instructions (host-blind)
  agents/RULES.md               # edit gate + memory routing (on-demand)
  agents/REVIEW.md              # PR / diff review triggers
  agents/PYTHON.md              # on-demand topic siblings
  agents/STREAMING.md
  agents/DOCS.md
  agents/DATABRICKS.md
  agents/AZURE-DEVOPS.md
  agents/JIRA.md
  agents/hosts/                 # per-product overlays
    copilot.instructions.md
  agents/repos/                 # per-git-remote exceptions (basename.md)
  agents/skills/                # shared skills (each folder has SKILL.md)
    watch-prs/
    watch-slack/
    optimize/
    ho/
    to/
  agents/bots/                  # optional: named bots + routines + workers
    AGENTS.md
    README.md
    general.md
    …
    skills/                     # bot workers (wake scripts, meters, …)
  bash/bash_aliases
  bash/bash_functions           # helpers (e.g. gmem for host memory paths)
  configs/                      # app configs (ghostty, grok, …)
  install.sh                    # symlinks into each tool home

Shared agents/AGENTS.md is host-blind: always-on rules that every tool should follow, with no product-specific framing. Product-only lessons live under agents/hosts/ as overlays the installer links into that product’s expected path. Topic siblings stay on-demand via a short catalog in the global file (name plus load trigger, not a digest of the sibling). Per-remote exceptions live under agents/repos/<basename>.md so one git remote can forbid a branch style or load review notes without polluting the global file.

Everything AI tools need lives under agents/. Shell helpers and app configs are included so a new machine is not only “agent rules” but a usable shell. Secrets stay out of plaintext git (encrypted or local env files the installer never publishes). Tool-local state — sessions, auth caches — stays outside the repo.

Note: The private clone URL of someone else’s dotfiles is not your bootstrap step. Put the same layout in your git-backed ~/dotfiles, then point each tool at it with an installer like the one below.

3. Layers That Feed the Hub

Symlinks only help if the content behind them is split by scope. Packing every lesson into the always-on file makes tools ignore it; scattering copies across tool homes brings drift back.

Layer Where it lives When it applies
Global instructions agents/AGENTS.md Always, every repo, every tool (host-blind)
Edit gate / memory routing agents/RULES.md Before editing any agents/ file or routing a lesson
Topic siblings agents/<TOPIC>.md When the catalog trigger matches
Per-remote notes agents/repos/<basename>.md When that git remote is the work
Host overlays agents/hosts/<product>.… That product only
Skills agents/skills/<name>/SKILL.md Recurring procedures / slash commands
Named bots agents/bots/<role>.md That bot’s host instruction field + routines
Project instructions <repo>/AGENTS.md Only that checkout

How-to-work that is always on belongs in the global file. A procedure you want the agent to load next time it does the same job belongs in a skill. Lessons that only make sense for one product belong in agents/hosts/. A fact about one repository belongs in that repository — or in the host’s workspace memory — not in your home rules.

Keep the global file thin. Prefer Never X — do Y, a concrete check, or a good/bad pair over adjectival vibes. Improve or merge beats append. Gate edits: do not casually grow agents/AGENTS.md from a random chat — load the edit gate first and get explicit approval before changing shared rules.

4. Per-Tool Setup via install.sh

Each tool expects a slightly different filename or skills path. The installer builds a small hub so one host-blind file feeds many names, and optionally links a per-product overlay when that file exists:

Path the tool looks at Points to
~/.agents/AGENTS.md ~/dotfiles/agents/AGENTS.md
~/.grok/Agents.md ~/.agents/AGENTS.md
~/.copilot/copilot-instructions.md ~/.agents/AGENTS.md
~/.copilot/instructions/dotfiles.instructions.md ~/dotfiles/agents/hosts/copilot.instructions.md
~/.grok/skills ~/dotfiles/agents/skills
~/.claude/skills same skills folder
~/.cursor/skills same skills folder
~/.copilot/skills same skills folder
~/.agents/skills/<name> ~/dotfiles/agents/skills/<name> (per skill)

How that plays out per tool:

  • Grok — instructions via ~/.grok/Agents.md → hub; skills via ~/.grok/skills → the shared tree. Optional: symlink ~/dotfiles/configs/grok → ~/.grok/config.toml so /settings writes land in git.
  • Copilot — shared rules via ~/.copilot/copilot-instructions.md → hub; Copilot-only overlay via ~/.copilot/instructions/dotfiles.instructions.md → agents/hosts/copilot.instructions.md (linked when that file is present); skills via ~/.copilot/skills.
  • Cursor — skills via ~/.cursor/skills → the same tree (Cursor also picks up in-repo AGENTS.md when you open a project).
  • Claude — skills via ~/.claude/skills → the same tree.

So there is one hub file (~/.agents/AGENTS.md) and several tool-specific names that all resolve to it. Host overlays stay separate so product-only guidance never pollutes the shared always-on file. Skills are shared the same way: most agent homes get a directory symlink at the whole agents/skills tree. The ~/.agents/skills home is special — it can also hold extras that are not in the repo — so the installer creates a real directory there and links each skill by name instead of replacing the whole folder.

Non-AI pieces that usually ship with the same installer:

Path Points to
~/.bash_functions ~/dotfiles/bash/bash_functions
~/.bash_aliases ~/dotfiles/bash/bash_aliases
~/.config/ghostty/config.ghostty ~/dotfiles/configs/ghostty
~/.grok/config.toml ~/dotfiles/configs/grok

Verify the instruction chain if you like:

➜ ls -l ~/.agents/AGENTS.md ~/.grok/Agents.md ~/.copilot/copilot-instructions.md
➜ ls -l ~/.copilot/instructions/dotfiles.instructions.md
➜ ls -l ~/.grok/skills ~/.cursor/skills ~/.claude/skills ~/.copilot/skills

You want every one of those to be a symlink that eventually lands under ~/dotfiles/agents/.

5. Memory Without Stuffing Rules

Not everything durable is a rule. Cross-repo process exceptions can graduate into global AGENTS.md. Project facts belong in the host’s workspace memory — not in the always-on file, and not in an invented MEMORY.md next to the work.

A practical routing table (the edit gate owns the full version):

Kind Home
Instruction (how to work) agents/*.md — global, topic sibling, or repos/<basename>.md
Recurring procedure the skill that should load when it recurs
Fact, many repos host built-in global memory
Fact, one repo host built-in workspace memory
Ephemeral host session scope if it has one; otherwise drop

Keep one home per lesson. If it already lived elsewhere, delete the copy. Never retain secrets, ephemeral errors, PR noise, or unchosen ideas in durable memory.

Shell helpers can still point at whatever path your host actually uses. In my tree, gmem resolves the current product’s workspace memory directory so you can open or inspect it without inventing a second store. Prefer the host’s built-in memory API when the tool has one; the helper is optional navigation, not a parallel database.

6. Skills and Agent Workflows

Skills are folders under ~/dotfiles/agents/skills/<name>/ with a SKILL.md (and optional scripts). They are the right home when the next session should load a procedure — watch PRs, watch Slack, hand work to another agent, optimize a harness’s token cost — anything you would otherwise re-explain every Monday.

Concrete names from my tree (yours will differ; the pattern is the same):

  • watch-prs / watch-slack — background watchers with a small contract the agent can read.
  • optimize — lower price-weighted token cost per completed task without dropping quality (map spend → safe changes → report).
  • ho / to — write a short per-repo handover brief, then pick it up in another session without replaying investigation.

install.sh links that skills tree into the common agent homes and per-skill into ~/.agents/skills/<name>. Add a skill once in your repo; re-run the installer; every linked tool sees it.

Keep the skill focused on the procedure. Cross-cutting always-on exceptions still belong in global AGENTS.md. Durable lessons that are not a procedure belong in memory (previous section), not in the skill body forever.

Workflow shape in the global file can stay provider-agnostic too: thin Before / During / After changing code sections that point at on-demand siblings (REVIEW.md, repos/<basename>.md) instead of embedding every forge CLI in the always-on file.

7. Named Bots and Routines

If your stack supports named agents with an instruction field, scheduled jobs, and webhooks, the same repo can own those roles without pasting host CLI names into every file.

A portable shape:

agents/bots/
  AGENTS.md       # how an agent edits this roster
  README.md       # apply steps, workers, bootstrap
  general.md      # one role file per bot
  secretary.md
  blogger.md
  skills/         # background workers (not host cron polls)

Each role file is YAML frontmatter, standing instructions, then a ### History snapshot that is never applied as the live prompt. Host jobs live under ## Routines (one ### per job, schedule in **When:**). Apply is two steps:

  1. Instruction field = text above History, minus ## Routines.
  2. Host jobs = each routine copied word-for-word from git (replace the old set).

Workers (scripts under agents/bots/skills/) do the polling, metering, and wake posts. Prefer a script over a host job that sits signed-in all week. Role files stay host-agnostic: no vendor VM paths, no product-only URLs — those belong in the bots README. Lasting behavior changes go through git on the default branch, then pull + re-apply; chat memory is not durable state.

You do not need named bots to benefit from the symlink hub. When you do add them, they become another consumer of the same instructions and skills tree — still one repo, still one installer on the Bot machine.

8. Bootstrap Your Own Dotfiles

Put the layout in your git-backed ~/dotfiles (private is fine; public works too if you keep secrets out). Then an installer that symlinks — illustrate with example paths, not someone else’s clone URL:

➜ # your repo already at ~/dotfiles (clone/pull however you normally do)
➜ ~/dotfiles/install.sh

A minimal install.sh pattern (no secrets, same idea as the full script):

#!/usr/bin/env bash
set -euo pipefail
REPO_DIR="$(cd "$(dirname "$0")" && pwd)"

link_path() {
  local src="$1" dest="$2"
  mkdir -p "$(dirname "$dest")"
  if [[ -L "$dest" || ! -e "$dest" ]]; then
    ln -sfn "$src" "$dest"
  elif [[ -f "$dest" || -d "$dest" ]]; then
    mv "$dest" "${dest}.bak.$(date +%Y%m%d%H%M%S)"
    ln -sfn "$src" "$dest"
  else
    echo "error: $dest exists and is not a file, dir, or symlink" >&2
    exit 1
  fi
}

AGENTS_SRC="$REPO_DIR/agents/AGENTS.md"
AGENTS_HUB="${HOME}/.agents"
mkdir -p "$AGENTS_HUB" "${HOME}/.grok" "${HOME}/.copilot"
link_path "$AGENTS_SRC" "${AGENTS_HUB}/AGENTS.md"
ln -sfn "${AGENTS_HUB}/AGENTS.md" "${HOME}/.grok/Agents.md"
ln -sfn "${AGENTS_HUB}/AGENTS.md" "${HOME}/.copilot/copilot-instructions.md"

COPILOT_HOST="$REPO_DIR/agents/hosts/copilot.instructions.md"
if [[ -f "$COPILOT_HOST" ]]; then
  mkdir -p "${HOME}/.copilot/instructions"
  link_path "$COPILOT_HOST" "${HOME}/.copilot/instructions/dotfiles.instructions.md"
fi

SKILLS_SRC="$REPO_DIR/agents/skills"
for home in "${HOME}/.grok/skills" "${HOME}/.claude/skills" \
  "${HOME}/.cursor/skills" "${HOME}/.copilot/skills"; do
  link_path "$SKILLS_SRC" "$home"
done

The script stays deliberately simple: for each destination it either creates a symlink, replaces an existing symlink, or moves a real file/dir out of the way to a timestamped .bak.… backup before linking. Missing sources should fail loudly instead of half-installing. Host overlays are optional — link them only when the file exists.

After it finishes you should see a short report of what was linked (instructions hub, optional host overlays, skills homes, shell helpers, a couple of app configs).

Note: Keep secrets out of plaintext git. Token files belong under something like an encrypted tree or a local env file the installer never symlinks into the world. Bot wake URLs and sender keys stay in ~/.env (chmod 600), never in the role files.

9. Edit Once, Propagate Everywhere

Because the destinations are links, you edit the repo (or any symlink path into it) and every tool that reads that path sees the change on the next session:

➜ $EDITOR ~/dotfiles/agents/AGENTS.md
➜ cd ~/dotfiles
➜ git add -p
➜ git commit -m "Tighten global agent safety rules"
➜ git push origin main

On another machine:

➜ cd ~/dotfiles && git pull origin main
➜ ~/dotfiles/install.sh

Re-running the installer is cheap. Existing symlinks are refreshed with ln -sfn; you only get a backup when something real is sitting where a link should be.

Skills follow the same rule. Drop a folder under ~/dotfiles/agents/skills/<name>/ with a SKILL.md, re-run install.sh, and every linked tool picks up the same skill tree without a per-tool copy step. Product-only lessons go in agents/hosts/, not in the shared host-blind file. Bot role or routine changes go through the same push; on a Bot machine a watch-dotfiles-style worker can pull and wake the representative to re-apply instruction fields and host jobs from git.

10. New Machine Checklist

A practical bootstrap order:

  1. Get your repo and link — clone or pull your ~/dotfiles, then run ~/dotfiles/install.sh.
  2. Shell — make sure your ~/.zshrc (or equivalent) sources the linked aliases/functions and puts any CLI you care about on PATH.
  3. Tool logins — install and authenticate each agent CLI / IDE the official way. Re-run install.sh if a Dock or launcher step was skipped because a binary was not on PATH yet.
  4. Workspace — keep project checkouts under something like ~/Projects. Global rules come from the dotfiles hub; per-repo nuance lives in that project’s own AGENTS.md (and optional agents/repos/<basename>.md for remote-wide exceptions).
  5. Optional bots — if you run named bots, apply role files in two steps (instructions, then routines), start worker scripts from the clone, and keep wake secrets in ~/.env.
  6. Optional extras — phone bridges, Dock shortcuts, and similar live beside the installer; only run them if you need them.

In short: one repo for the files you maintain, one installer that creates the symlinks, many tools (and optional bots) reading the same content. Next time you add an agent, check whether it already has a home in install.sh — and if not, add one symlink instead of another pasted instructions file.
